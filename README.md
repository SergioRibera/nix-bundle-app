# nix-bundle-app

Turn any Nix derivation into native installers for **Linux**, **macOS**, and **Windows** — no Nix required on the target machine.

It does *not* build your program. You hand it a pre-built derivation (e.g. `pkgs.hello`, your crane/cargo build, anything that produces `bin/`), and it emits installable artifacts plus the manifests each OS expects.

| OS      | Formats                                                                                |
|---------|----------------------------------------------------------------------------------------|
| linux   | `deb`, `rpm`, `archlinux`, `appimage`, `flatpak`, `snap`, `brew` (linuxbrew), `tar.gz`, `tar.xz`, `tar.zst`, `zip` |
| darwin  | `app`, `dmg`, `pkg`, `productbuild`, `brew`, `tar.gz`, `tar.xz`, `tar.zst`, `zip`      |
| windows | `nsis` (`.exe`), `msi`, `tar.gz`, `tar.xz`, `tar.zst`, `zip`                           |

Full autogenerated reference + programmatic access (`bundler.linuxTargets`, `bundler.darwinTargets`, …) in **[docs/targets.md](docs/targets.md)**.

Bundles ship unsigned out of the Nix sandbox. Opt-in codesigning hooks drop a turnkey `sign.sh` next to each artifact — see [Codesigning](#codesigning).

## Quickstart

[`overlay.nix`](overlay.nix) *is* nix-bundle-app. Apply it to any `pkgs` and
get `pkgs.nixBundleApp` for free:

```nix
let
  nix-bundle-app = builtins.fetchTarball {
    url = "https://github.com/SergioRibera/nix-bundle-app/archive/<rev>.tar.gz";
    sha256 = "..."; # pin a real commit + hash
  };
  pkgs = import <nixpkgs> {
    overlays = [ (import "${nix-bundle-app}/overlay.nix") ];
  };
in
pkgs.nixBundleApp.bundle {
  drv = pkgs.hello;
  format = "deb";
  info.maintainer = "You <you@example.com>";
}
```

`nix-build -E '...' -A hello-deb` (or wrap the above in your own `default.nix`)
→ artifact lands in `result/`. See [`examples/hello`](examples/hello) for a
complete consumer that builds several formats at once.

## API

```nix
bundler.bundle    { drv; format; info ? {}; target ? null; }
bundler.bundleAll { drv; formats; info ? {}; target ? null; }
bundler.release   { info; matrix; releaseUrl; installScripts ? true; }
bundler.signedApp { bundle; name ? "${bundle.name}-sign"; }

bundler.formats          # [ "app" "appimage" … ]   — all supported formats
bundler.linuxTargets     # formats producible for target.os = "linux"
bundler.darwinTargets    # ... darwin
bundler.windowsTargets   # ... windows
bundler.targets.<os>     # grouped form (linux | darwin | windows | any)
bundler.formatOS         # raw { format = os | "any" | [os…]; } map
```

`bundler` above is `pkgs.nixBundleApp` once the overlay is applied — it groups everything that builds derivations or shells out.

Pure, pkgs-independent helpers (string/attrset rendering, no building) live under `pkgs.lib.nixBundleApp` instead, since they're genuine library material:

```nix
pkgs.lib.nixBundleApp.utils      # parseSystem, normalizeTarget, xmlEscape, …
pkgs.lib.nixBundleApp.desktop    # XDG .desktop entry rendering
pkgs.lib.nixBundleApp.services   # systemd/launchd/NSIS/MSI service rendering
pkgs.lib.nixBundleApp.normalize  # info.* schema validation/defaulting
```

`target` defaults to `drv.system`; pass `{ arch = "x86_64"; os = "windows"; }` (etc.) for cross-bundling. `info` is validated at evaluation time against [`lib/schema.nix`](lib/schema.nix) — the full reference lives in **[docs/options.md](docs/options.md)** (autogenerated).

## Two features worth knowing about

### Declarative desktop entries + services

XDG `.desktop` files and cross-OS services are declared as Nix structs, not raw files:

```nix
info.desktopEntries = [ { name = "Hello"; exec = "/opt/hello/bin/hello %F"; categories = [ "Utility" ]; } ];
info.services = [
  { name = "hello-agent"; exec = "/opt/hello/bin/hello --daemon"; description = "Background greeter"; }
];
```

A single service struct materialises as:

| OS              | Output                                                                          |
|-----------------|---------------------------------------------------------------------------------|
| linux           | `/lib/systemd/system/<name>.service`, enabled on `postinst`                     |
| darwin (`.pkg`) | `/Library/LaunchDaemons/<label>.plist`, loaded by `postinstall`                 |
| windows (NSIS)  | `install-services.bat` / `uninstall-services.bat`, run from installer sections  |
| windows (MSI)   | Native `<ServiceInstall>` + `<ServiceControl>` rows                             |

Full per-OS overrides (systemd unit/service kvs, launchd processType, sc.exe account/start/errorControl, …) are in [docs/options.md](docs/options.md).

### Extra system files (linux installer formats)

`info.extraFiles` drops arbitrary files into the staged tree at fixed install paths — udev rules, modprobe.d snippets, modules-load.d, polkit policies, AppArmor profiles, anything that needs to land outside `/opt/<name>`. Honoured by `deb`, `rpm`, `archlinux`.

```nix
info.extraFiles = {
  "/lib/udev/rules.d/61-hello.rules" = ./contrib/hello.rules;
  "/etc/modprobe.d/hello.conf"       = "options hello_mod debug=1\n";
  "/etc/modules-load.d/hello.conf"   = ./contrib/modules-load.conf;
};
```

Values can be a Nix path / store path (copied verbatim) or an inline string (materialised via `pkgs.writeText`). When any destination lands under a known udev rules directory the post-install hook also runs `udevadm control --reload-rules && udevadm trigger` so freshly-installed rules take effect without a manual reload.

Ignored by `appimage`, `flatpak`, `snap` (no system install location) and by darwin/windows formats.

### Auto-discovered distro deps

`info.autoDepends = true` (default) makes the deb/rpm/archlinux formats scan staged binaries with `patchelf --print-needed` and look each SONAME up in [`lib/lib-map.nix`](lib/lib-map.nix) (libc family, openssl, zlib, glib/gtk/qt, X11/wayland, dbus/systemd…). Discovered deps are merged with explicit `info.depends.<distro>`; auto-detected entries never replace user ones. Unknown SONAMEs are dropped silently.

Set `info.autoDepends = false` to fall back to literal user lists.

## What happens under the hood

1. Walk the runtime closure of `drv` via `pkgs.closureInfo`.
2. Copy every shared library into the bundle (`/opt/<name>/lib`, `Contents/Frameworks`, next-to-`.exe`), skipping the base libs each target ships (libc, libm, libpthread, libdl, ld-linux, libSystem, libobjc, …).
3. Patch binaries: linux → `patchelf --set-interpreter` + `--set-rpath '$ORIGIN/../lib'`. darwin → `install_name_tool -change` rewrites `/nix/store/...` to `@executable_path/../Frameworks/<lib>`. windows → no patching, DLLs sit next to `.exe`.
4. Generate manifest (control, spec, PKGINFO, Info.plist, Distribution xml, .nsi, .wxs, AppRun, …).
5. Pack with the right tool (`dpkg-deb`, `rpmbuild`, `bsdtar+zstd`, `xorrisofs`, `makensis`, `wixl`, `xar+cpio+bomutils`, `mksquashfs`, `tar`, `zip`).

## Format-specific notes

- **`appimage`**: AppDir + SquashFS appended to a pinned [type2-runtime](https://github.com/AppImage/type2-runtime) ELF. Override the runtime via `info.appImageRuntime`. `AppRun` exports `LD_LIBRARY_PATH` so bundled libs win.
- **`pkg`** (macOS): flat `.pkg` (xar). Without services the `.app` goes to `/Applications/<name>.app`. With services, `install-location="/"` and a `postinstall` script `launchctl load -w`s each plist. Linux host uses `xar+cpio+bomutils`; darwin host uses `pkgbuild`.
- **`productbuild`**: distribution-style installer wrapping the component `pkg`. `info.productbuild = { welcome; license; readme; conclusion; background; title; organization; allowCustomize; }` controls the screens. On darwin runs real `productbuild`; on linux hand-assembles the outer xar (Distribution + Resources + component pkg).
- **`brew`**: works on **macOS and linuxbrew**. Produces `Formula.rb` + `.tar.gz`. Darwin + `info.services` gets a `service do … end` block (launchd integration).
- **`msi`**: `msitools`' `wixl`. `UpgradeCode` derived from `bundleId` — pin `info.msiUpgradeCode` for released artifacts. Services materialise as native `<ServiceInstall>` + `<ServiceControl>` (no `.bat`).
- **`dmg`** on linux: HFS+ hybrid ISO via `xorrisofs -hfsplus` (not a byte-identical UDIF DMG; Finder mounts it fine).
- **`flatpak`**: emits a build-ready source layout (`<bundleId>.yaml` manifest + `<name>-<ver>.tar.gz` source tarball + `build.sh` helper). Doesn't produce the final `.flatpak` itself — that requires network access to fetch runtimes, which Nix sandbox forbids. Run `./build.sh` on a flatpak-builder-capable host (it shells out to `flatpak-builder --repo=repo build <appid>.yaml && flatpak build-bundle …`). Tune sandbox permissions with `info.flatpak.finishArgs`, runtime via `info.flatpak.runtime{,Version}`.
- **`snap`**: emits a `snap/snapcraft.yaml` + staged `payload/` + `build.sh` helper. Real `.snap` requires `snapcraft pack` which spins an LXD/multipass VM — not viable inside Nix sandbox. Run `./build.sh` on a snapcraft-enabled host. Tune confinement via `info.snap.confinement` (`strict`/`classic`/`devmode`), interfaces via `info.snap.plugs`, base via `info.snap.base` (`core22` ↔ Ubuntu 22.04).
- **`archlinux`**: by default emits a binary `*.pkg.tar.zst` (install with `pacman -U`) AND an AUR-publishable `aur/` subdir (`PKGBUILD` + `.SRCINFO` + `<name>-bin-<ver>-<arch>.tar.gz`). Toggle via `info.archlinux.output = "pkg" | "aur" | "both"` (default `"both"`). Set `info.downloadUrl` so the generated PKGBUILD's `source=()` + `sha256sums=()` point at your release tarball. Push `aur/` to `aur:<name>-bin.git`.

## Universal install script (cargo-dist style)

`bundler.release { … }` produces a flat directory with every bundle artifact + `install.sh` + `install.ps1` + `SHA256SUMS`. Ready to upload as a GitHub release in one shot. End-users do:

```sh
curl -fsSL https://github.com/user/repo/releases/latest/download/install.sh | sh
```

or on Windows:

```powershell
iwr https://github.com/user/repo/releases/latest/download/install.ps1 | iex
```

The scripts auto-detect (`uname -s`/`-m` resp. `$env:PROCESSOR_ARCHITECTURE`), pick the right bundle for the host, download it, verify against `SHA256SUMS`, extract, and drop the binary into `~/.local/bin` (Unix) or `%LOCALAPPDATA%\Programs\<name>` (Windows). Flags: `--version vX.Y.Z` to pin, `--dir <path>` to override install dir, `--uninstall` to remove.

```nix
packages.hello-release = bundler.release {
  info = { name = "hello"; version = "1.0.0"; license = "MIT"; };
  releaseUrl = "https://github.com/user/repo/releases/download/v\${VERSION}";

  matrix = {
    "x86_64-linux"    = { drv = helloLinux;    formats = [ "tar.gz" "deb" "rpm" ]; };
    "aarch64-linux"   = { drv = helloLinuxArm; formats = [ "tar.gz" ]; };
    "x86_64-darwin"   = { drv = helloMac;      formats = [ "tar.gz" "dmg" ]; };
    "x86_64-windows"  = { drv = helloWindows;  formats = [ "zip" "msi" ]; };
  };

  installScripts = true;   # default; set to false for raw bundles + SHA256SUMS only
};
```

The matrix declares each cross-compiled `drv` once + the formats to produce per target. `bundler.release` calls `bundle` for every (target, format) combo, reads `passthru.outFile` to learn each artifact's filename, hashes them, and bakes the (arch, os) → filename table into the generated scripts. No manual filename plumbing.

`bundler.installScripts { … }` (same args) returns just the scripts, without the bundle artifacts — useful when you publish bundles separately.

## Codesigning

Secrets (private keys, p12 passwords) cannot safely live in `/nix/store`, so the actual signing runs **after** `nix build`. Each format checks `info.signing.<os>.enable`; when true, a turnkey `sign.sh` lands next to the artifact. You run it with secrets passed via env vars:

```nix
info.signing = {
  darwin = {
    enable = true;
    p12File = ./certs/developer-id.p12;
    teamId  = "ABC1234567";
    hardenedRuntime = true;
    entitlements = ./entitlements.plist;
  };
  windows = {
    enable = true;
    pkcs12File = ./certs/auth.pfx;
    timestampUrl = "http://timestamp.sectigo.com";
  };
  linux = {
    enable = true;
    keyId = "0xABCDEF1234567890";
    style = "embedded";    # `embedded` → dpkg-sig/rpmsign; `detached` → *.sig
  };
};
```

```sh
nix-build -A hello-deb
P12_PASSWORD="$(cat ~/.secrets/p12.pw)" ./result/sign.sh           # darwin/windows
GPG_KEY_ID=0xABCDEF1234567890           ./result/sign.sh           # linux
```

### One-shot build + sign (no manual step)

`bundler.signedApp { bundle = …; }` returns a runnable derivation that stages a fresh copy of the (pure, cacheable) bundle and signs it in your shell where env vars are available:

```nix
hello-deb-signed = bundler.signedApp { bundle = bundler.bundle { drv = pkgs.hello; format = "deb"; info = { ... }; }; };
```

```sh
nix-build -A hello-deb-signed -o sign-hello-deb
GPG_KEY_ID=0xABCDEF1234567890 ./sign-hello-deb/bin/hello-deb-sign -- ./dist
# → ./dist/<name>.deb (signed) — sign.sh is removed from the output
```

Pass `--` followed by a target dir, or omit it for a fresh `mktemp -d`. The underlying bundle derivation stays cached; only the sign step is impure (your shell).

Signers used: `rcodesign` (macOS, cross-platform), `osslsigncode` (Authenticode), `dpkg-sig` / `rpmsign --addsign` (embedded GPG) or `gpg --detach-sign` (detached `.sig`).

## Caveats

- **`install_name_tool`** only runs on a darwin host. Linux→darwin bundles copy dylibs but skip load-path rewriting.
- **`mkbom`** (bomutils 0.2 in nixpkgs) crashes under modern glibc FORTIFY checks. Linux-built `.pkg` falls back to an empty Bom — most installers tolerate it. Build on darwin for a compliant Bom.
- **AppImage runtime** pinned to a numbered [type2-runtime](https://github.com/AppImage/type2-runtime) release (`lib/formats/appimage.nix`'s `runtimeRelease`); supply your own via `info.appImageRuntime` to pin something else.
- **SONAME map** is curated, not exhaustive. Add unknown deps via `info.depends.<distro>`.
- **Target verification**: formats that stage a raw binary check it with `file` against `target.{os,arch}` and fail the build on a mismatch. `msi`/`nsis` embed the exe inside a built container and aren't checked this way.

## Validation

`info` runs through `lib.evalModules` (same machinery as NixOS modules) before any derivation builds. Typos, type mismatches, missing required fields, and cross-field assertions (e.g. `format = "appimage"` + `info.services != []`, or a malformed `msiUpgradeCode`) fail at `nix-instantiate` time with helpful "Did you mean …?" hints.

## Tests

`nix-build tests` builds every format against `pkgs.hello` and a sample Rust binary, then verifies artifact filenames + payload sanity. [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs the same checks on `ubuntu-latest` and `macos-latest` (plus `nixfmt --check` and `deadnix` on the former), since neither host alone can produce every format: `rpm`/`nsis` need a real x86_64-linux, and `app`/`pkg`/`productbuild`/`brew`/darwin services need a real darwin binary, which nixpkgs can't cross-compile from linux. Each host skips the checks it can't produce.

[`examples/hello`](examples/hello) is a complete consumer showcasing several formats at once; `examples/default.nix` is the larger internal fixture the tests build against.
